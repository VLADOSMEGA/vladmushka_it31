# Практична робота №20
## Створення та застосування Views у PostgreSQL

### 1. Завдання 1. Подання-фільтр

Створено подання `active_loans`, яке показує лише неповернуті книги (`return_date IS NULL`).

Це дозволяє швидко переглядати активні позики без повторного написання умови WHERE у кожному запиті.

### 2. Завдання 3. Запис через просте подання

Виконано INSERT безпосередньо через подання `active_loans`. Запис успішно додано до базової таблиці `loans`.

Колонка `return_date`, яку не було вказано під час вставки, отримала значення NULL. Це стандартне значення для колонки без DEFAULT.

### 3. Завдання 4. Матеріалізоване подання

Створено матеріалізоване подання `active_loans_mat`.

Після додавання нового запису звичайне подання одразу показало оновлену кількість позик, а матеріалізоване залишило попереднє значення.

Після виконання REFRESH MATERIALIZED VIEW матеріалізоване подання оновилося.

Отже, звичайне VIEW виконує запит щоразу під час звернення, а MATERIALIZED VIEW зберігає результат запиту до наступного оновлення.

### 4. Завдання 6. Можливість змінювати подання

Подання `loans_with_books` створено з використанням JOIN таблиць `loans` і `books`. Спроба INSERT завершилася помилкою SQLSTATE 55000, оскільки PostgreSQL не підтримує автоматичне додавання записів через таке подання.

До `active_loans` додано WITH CHECK OPTION.

Вставка запису з `return_date = NULL` пройшла успішно, оскільки відповідала умові WHERE.

Вставка запису з датою повернення була відхилена з помилкою SQLSTATE 44000. WITH CHECK OPTION не дозволяє додавати через подання рядки, які не відповідатимуть його умові.

### 5. Контрольні запитання

1. Звичайне VIEW не зберігає власні дані, а щоразу виконує запит до базових таблиць. MATERIALIZED VIEW зберігає результат запиту, тому потребує місця для зберігання.

2. Колонка поза SELECT подання отримала NULL, оскільки для неї не було вказано значення або DEFAULT. Умова WHERE лише фільтрує записи, а не встановлює значення колонок.

3. MATERIALIZED VIEW доречно використовувати для великих звітів про позики бібліотеки, які не потрібно оновлювати після кожної зміни. Це дозволяє швидше отримувати результати складних запитів.

4. Подання з JOIN об'єднує декілька таблиць, тому PostgreSQL не може автоматично визначити, у яку саме таблицю потрібно додати запис. Просте подання над однією таблицею може підтримувати INSERT.

5. WITH CHECK OPTION перевіряє, чи відповідає новий або змінений рядок умові WHERE подання. Воно захищає від додавання записів, які після вставки не відображатимуться в цьому поданні.

### 6. Висновок

Під час практичної роботи створено звичайне та матеріалізоване подання, перевірено автоматичне оновлення VIEW і ручне оновлення MATERIALIZED VIEW. Виконано вставку через просте подання, перевірено обмеження для подань із JOIN та застосовано WITH CHECK OPTION.
